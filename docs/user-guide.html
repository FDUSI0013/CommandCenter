Operator manual

AI Command Center

Running agents you did not write

FD AI Command Center is an AI agent governance console. Teams register the agents they run, connect them with an SDK or over OpenTelemetry, and then govern them: what they may call, what they cost, what they were asked, what they answered, and what has to be approved before they act.

What this is

The product is twenty-five screens over one API, split down the middle by a deliberate architectural line.

Governance is yours. Agents, connections, connectors, policies, approvals, the audit chain, secrets, quotas, budgets, deployments and licences live in tables this platform owns, with role checks and an append-only, hash-chained audit trail.

Telemetry belongs to the engine. Runs, traces, spans, feedback scores, prompts, datasets, experiments and costs live in a private telemetry engine reached through one adapter. It is not addressable from outside; the server in front of it is the sole identity authority, and one workspace maps to one project namespace inside it.

That line matters when something breaks. If the engine is unreachable, telemetry screens fail closed with a plain telemetry_unavailable message and the governance half keeps working. You will never see a fabricated zero standing in for a number nobody measured.

The one rule worth internalising

Nothing in this console is simulated. If a number is on screen, a service computed it. If a service cannot answer, the screen says so instead of showing a zero. A dash means not measured, and that is not the same thing as zero.

How the pieces fit

   an agent  --SDK or OTLP-->  +------------------+
                              |    the server    |  the only public surface
   the console ------------->  |  (FastAPI)       |  identity . tenancy . governance
                              +--------+---------+
                                       |  private network, no published port
                              +--------v---------+
                              | telemetry engine |  traces . spans . scores . prompts
                              +------------------+  datasets . experiments . costs

Core concepts

Nine words carry most of the product. Learn these and the screens explain themselves.

TermWhat it means here
WorkspaceA tenant. Every query filters on it, so another workspace's row is indistinguishable from a row that does not exist. One person can belong to many workspaces: identity is global, access is per-workspace.
AgentA registered thing that runs. Registration creates its private namespace in the telemetry engine, so an unregistered agent has nowhere to report and is invisible to every telemetry read.
RunOne execution: a question in, an answer out. A row on Live Runs. Internally a trace.
SpanOne timed step inside a run, typed general, llm, tool or guardrail. Spans nest, and the nesting is the agent's real decision path.
ConnectorSomething an agent is permitted to call: an MCP server, an API, a database, a vector store, a custom tool. Registered by a human and granted to agents, never auto-discovered from traffic.
PolicyA rule evaluated on the way in, before telemetry is stored. Scoped Global, Environment, Agent or Connector, enforced as Block, Require Approval, Escalate, Mask, Route, Throttle, Warn or Log Only.
GuardrailA runtime safety filter: prompt injection, PII, toxicity, hallucination, secrets. Produces events you read on the Guardrails screen.
Quota / budgetA spend or usage ceiling checked before a run is accepted, not tallied afterwards.
EntitlementWhat a licence plan permits. Checked at ingest, so an unlicensed capability is refused rather than billed.

What happens when an agent reports

Every batch, from the SDK or from OpenTelemetry, walks the same path. This is worth knowing because it explains why things get refused.

  1. Authenticate the API key and resolve which agent it may write for.
  2. Evaluate policies that reach that agent, by binding or by scope.
  3. Run guardrail checks. A Block verdict refuses the item; Mask strips the content and keeps the record.
  4. Check licence entitlement and quota.
  5. Only then hand the telemetry to the engine, and commit the evidence — violations, guardrail events, quota consumption — in the same transaction.

An agent therefore cannot opt out of governance by lying to the SDK. The SDK is a reporter; the server is the enforcer.

Violations, escalations and hand-offs: one definition everywhere

Three figures appear on more than one screen. Each has exactly one definition, and every screen that shows it counts the same records for its own window and scope.

FigureWhat it countsWhere you see it
Policy violationsViolation events recorded by the enforcement path at ingest (step 5 above): one for each policy an item matched, and one for each violation an agent reported itself with log_policy_violation() (Python) or policyViolation() (TypeScript). These are the records the Policy Center counts, whatever the enforcement, including those of agents since removed from the registry.Live Runs, Policy Center, Agent Registry, Agent Detail
Human escalationsThose violations whose recorded enforcement was Escalate or Require Approval: the ones that put a person in the loop. A subset of policy violations, never more than them.Live Runs, Policy Center, Agent Detail
Agent hand-offsRuns the agent itself reported as escalated to a human. A statement the agent made in its own telemetry, not a policy outcome, so it is counted separately and never added to human escalations.Live Runs

Same records, different windows

Live Runs counts over the window selected in its Time Range filter — the last hour, 6 hours or 24 hours. The Policy Center counts over 30 days. Both read the same violation records, so the numbers agree when the windows do; a Live Runs figure smaller than the Policy Center's is the shorter window, not a missing record. The Agent Registry's Policy Violations card counts the whole workspace over 30 days, and Agent Detail shows one agent's figures over 30 days.

Two things that sound similar are not these figures. The Approvals & Audit screen's Escalated Requests (30d) count is approval requests an approver has passed to a senior reviewer: a status of a request in the queue, not a count of violations. The Metrics chart's escalations line, by contrast, is Human Escalations exactly as defined above, narrowed by the agent filter like every other line. LLM Usage shows, per model, only the violation records it can tie to one of that model's runs, so its per-model counts add up to less than the window's total whenever a record names no stored run (see LLM Usage).

Signing in and roles

Open the console and sign in with your work email and password. Sessions are signed tokens in an httpOnly cookie, so several people, and the same person on several devices, can be signed in at once without interfering with each other.

With one deliberate exception: changing a password ends every other session on that account, wherever it is open, and so does an administrator resetting it. That is usually the reason someone changes a password, so it is not treated as a side effect. The device doing the changing stays signed in; the others are asked to sign in again the next time they call. A deployment-progress tab left streaming closes within half a minute. A Live Runs tab closes on the next run it would have shown you — so a workspace where nothing is running may hold the connection open, delivering nothing, until it ages out. An API key is unaffected — it is not a session and has no password — so a key that should also be withdrawn has to be revoked under Workspace Settings.

Agents never use a password. They authenticate with an API key, issued under Workspace Settings.

The six roles

RoleCan do
ownerEverything, plus billing, licensing and workspace deletion. Only an owner may grant the owner role.
adminEverything except billing. Issues API keys, manages members, edits policies and secrets.
operatorRun, deploy and approve. No policy or secret edits.
approverApprove, reject and escalate only.
memberRead, and author prompts, tests and feedback.
viewerRead only.

Roles are enforced on the server, not in the interface. A control you may not use is disabled and says why on hover, and the endpoint behind it refuses the call regardless of what the interface showed you.

Connect your first agent

Four steps, five minutes. Do them in order — an ingest key cannot be bound to an agent that does not exist yet.

1. Register the agent

Agent Registry → New Agent. Name it, pick a platform (Azure AI Foundry, Copilot Studio, M365 Copilot, Power Platform or Custom Agent), an environment, an agent type (Pro-code, Low-code, Copilot) and a risk level. Then Activate it — new agents start in Pending Review, and an inactive agent cannot ingest.

2. Issue an API key bound to it

Workspace Settings → API Access Tokens → Issue Key. Name it, leave the scopes at ingest and read, and — this is the part worth doing — set Bind to agent to the agent you just created. A bound key can only ever write that agent telemetry, so a leaked key cannot impersonate the rest of your fleet.

The key is shown once

The server stores only a SHA-256 hash. When the mint dialog closes, the plaintext is gone for good and the table keeps a hint like fo_live_263...lgga. Copy it before you close. If you lose it, revoke the key and mint another.

3. Point your agent at the platform

export FULCRUM_OPS_API_KEY=fo_live_...
export FULCRUM_OPS_BASE_URL=https://your-server/api/v1
export FULCRUM_OPS_WORKSPACE=your-workspace-slug

4. Instrument and run

import fulcrum_ops
from fulcrum_ops import trace

fulcrum_ops.configure(agent="Support Bot", environment="Production")

@trace
def answer(question: str) -> str:
    return "..."

answer("where is my order?")
fulcrum_ops.flush()

Open Live Runs. The run appears within a few seconds.

The Python SDK: install and configure

The SDK package is fulcrum-ops (import name fulcrum_ops). It needs Python 3.9 or newer and has exactly one runtime dependency, httpx.

The server serves it: the SDK is its client, versioned with the API it speaks to, and anything that can report telemetry can already reach the host. No credentials and no extra login — just point pip at the index alongside your usual one, so the SDK's single dependency (httpx) still resolves normally:

pip install --extra-index-url https://controlplane.fdprod.net/pypi/simple fulcrum-ops
pip install --extra-index-url https://controlplane.fdprod.net/pypi/simple "fulcrum-ops[openai]"

Every deployment serves its own matching build at /pypi/simple, so use the host your agents report to. The wheel is immutable: a version is published once and never rebuilt.

Extras: openai, anthropic, langchain, dev. None of the provider packages is a hard dependency — the wrappers import lazily. For an air-gapped install, download the wheel the index points at and install the file directly: pip install ./fulcrum_ops-1.0.2-py3-none-any.whl.

Two ways to configure

A module-level default client, which decorators find on their own:

import fulcrum_ops

fulcrum_ops.configure(
    agent="Support Bot",
    environment="Production",
    api_key="fo_live_...",              # or FULCRUM_OPS_API_KEY
    base_url="https://host/api/v1",     # or FULCRUM_OPS_BASE_URL
)

Or an explicit client, which is a context manager that flushes and closes on exit:

from fulcrum_ops import FulcrumOps

with FulcrumOps(agent="Batch Job", environment="Staging") as client:
    with client.span("work", type="tool") as s:
        s.set_output({"rows": 128})

Your platform team can tighten these remotely

At start-up the SDK fetches /ingest/config and narrows its own options to whatever the deployment enforces. Sampling and batch limits take the lower of local and server; capture flags are a conjunction, so either side can switch content capture off and neither can switch it back on. A platform team can therefore disable prompt capture across an entire estate and no agent-side setting can override it.

Tracing runs

@trace is the whole beginner API. The outermost decorated call opens a run; nested decorated calls become child spans automatically, because parentage travels in a contextvar rather than through your function signatures.

from fulcrum_ops import trace

@trace(name="retrieve", type="tool")
def retrieve(question: str) -> list[str]:
    return ["doc-1", "doc-2"]

@trace                       # bare form works too
def answer(question: str) -> str:
    docs = retrieve(question)     # becomes a child span
    return f"Based on {len(docs)} docs..."

It handles all four callable shapes — plain functions, coroutines, generators and async generators — and drops self/cls when it binds arguments.

ArgumentMeaning
nameSpan name. Defaults to the function name.
typegeneral, llm, tool or guardrail.
capture_input / capture_outputOverride capture for this function only — useful on one function that handles secrets.
metadata, tagsAttached to the span.
agent, thread_idOverride the agent, or group runs into a conversation.
clientUse a specific client instead of the module default.

Spans, models and usage

Open spans by hand when you want to describe what happened inside a step:

client = fulcrum_ops.get_client()

with client.span("generate", type="llm") as span:
    span.set_model("gpt-5", "azure")
    span.set_input({"prompt_tokens_est": 180})
    reply = call_the_model()
    span.set_usage(prompt_tokens=180, completion_tokens=42)
    span.set_output(reply)
    span.score("grounded", 1.0, reason="cites retrieved doc")
MethodUse it for
set_input(value) / set_output(value)What went in and came out.
set_model(model, provider)The model that served the call. Report what actually ran, not a deployment alias — cost tables are keyed on the real model name.
set_usage(prompt_tokens=, completion_tokens=)Measured tokens. Prefer the provider response over an estimate.
set_cost(cost)State cost yourself when you know it better than the engine.
set_metadata(**kw) / add_tags(*t)Arbitrary structure for filtering later.
log(message, **fields)A structured log line inside the span.
score(name, value, reason=)A quality score on this span.
record_exception(exc)Attach a failure without raising.

Getting cost to resolve

Cost is computed from model plus provider. If either is missing or spelled in a vocabulary the price table does not use, cost comes back zero. Azure-served OpenAI models want provider azure, not azure-openai, and the real model name rather than a deployment alias — this is yours to get right on a hand-written span, while track_openai (below) detects the Azure case for you. A span with no open trace opens one around itself, so a stray client.span(...) still produces a valid run.

Scores and feedback

A score attached to an open span or trace travels inside that payload. A standalone score posts separately, which is how you record a judgement that arrives later — a thumbs-up an hour after the run, or an offline evaluation result.

with client.span("answer", type="llm") as s:
    s.score("faithfulness", 0.93, reason="all claims cited")

client.score(trace_id, "user_rating", 1.0, target="trace")
client.log_feedback(trace_id=trace_id, rating=1, body="fixed my problem")

target is trace, span or thread. Scores show up on Live Runs, feed the Evaluations trend, and are what Feedback and Quality Loop aggregates.

Feedback in the shapes products actually collect

log_feedback is the general form. These wrap it so a caller never has to remember that sentiment is a string or that a rating is 1–5:

client.thumbs_up(trace_id)
client.thumbs_down(trace_id, "wrong account")
client.rate(4, trace_id, comment="close, missed the caveat")
client.report_issue("Cites stale pricing", severity="High", trace_id=trace_id)

Each is also available at module level — fulcrum_ops.thumbs_up(...) — like flush(). rate() derives sentiment from the score and treats the midpoint as neutral rather than positive: three out of five is not praise, and counting it as praise would flatter every quality report built on the signal. report_issue() is for the agent noticing its own failure — a retrieval that returned nothing, a tool that answered nonsense — rather than waiting for a person to complain. It travels as negative feedback: a feedback.submitted event with the source Agent Response Rating, which lands in the Feedback inbox on Feedback & Quality Loop with the title leading the body and any detail= underneath it. severity is Critical, High, Medium or Low and is kept as structured metadata on the feedback row, so nobody has to read it back out of the sentence. It does not put a row on the Issues tab by itself — issues are raised from themes on that screen, from this feedback among the rest.

Guardrails and policy violations

When your agent runs its own safety check, report the verdict so the platform can govern on it:

client.log_guardrail_event(
    "PII scan",
    action_taken="Warn",          # Warn | Block | Mask | Log
    score=0.9,
    matched={"EMAIL": 1, "PHONE": 2},   # a mapping, not a list
    sample=text[:80],
    trace_id=trace_id,
)

client.log_policy_violation(
    "No external email without approval",
    severity="High",
    detail={"attempted_recipient": "gmail.com"},   # a mapping, not a string
)

Two shapes that bite

matched must be a mapping of label to count, not a list of labels, and detail on a policy violation must be a mapping too; a string or a list is accepted locally and rejected by the server. action_taken is one of Warn, Block, Mask or Log — casing and common variants (Warned, Blocked) are normalised server-side, but there is no Passed. Watch on_error during first integration and these show up immediately.

Provider wrappers

Rather than writing llm spans by hand, wrap the provider client and every completion call becomes a span with the model, usage and output already filled in.

from openai import OpenAI, AzureOpenAI
from anthropic import Anthropic
from fulcrum_ops.integrations import track_openai, track_anthropic

openai = track_openai(OpenAI())
azure  = track_openai(AzureOpenAI(...))    # reported under provider "azure"
claude = track_anthropic(Anthropic())

The provider is detected, because cost depends on it. track_openai reports provider azure for an AzureOpenAI client and for the plain client an Azure AI Foundry project hands back — it recognises the class name, and failing that an endpoint on openai.azure.com, cognitiveservices.azure.com or services.ai.azure.com. Everything else is openai. Pass provider= to override the detection when you are served from somewhere it cannot see.

Pass model= when neither the call nor the response names a model, which is the case for a Foundry agent addressed by agent_reference; it is used only as the fallback, so a response that does name its model still wins:

openai = track_openai(project_client.get_openai_client(), model="gpt-5")
openai.responses.create(input=[...], extra_body={"agent_reference": {...}})

Streaming responses keep the span open until the stream is exhausted, so a streamed answer is timed correctly rather than closing at first token. For LangChain, use the callback handler, which takes the provider from LangChain's own ls_provider and files azure-openai under azure for the same reason:

from fulcrum_ops.integrations import FulcrumOpsCallbackHandler

chain.invoke(payload, config={"callbacks": [FulcrumOpsCallbackHandler()]})

Prompts

Prompts authored in Prompt Studio can be pulled at runtime, so changing a system prompt does not require a redeploy.

from fulcrum_ops import get_prompt, template_variables

p = get_prompt("support-system-prompt")        # cached; server is revalidated
print(template_variables(p.template))          # ['customer_name', 'tier']
text = p.format(customer_name="Dana", tier="gold")

The prompt version used is recorded on the run, so a quality regression can be traced back to the exact wording that produced it.

Datasets and experiments

Offline evaluation: build a dataset of cases, run a candidate against it, and get a scored result you can compare on the Evaluations screen.

Build the dataset through the client's datasets handle:

client = fulcrum_ops.get_client()

client.datasets.create("support-golden", description="Answers we agree are correct")
client.datasets.add_items("support-golden", [
    {"input": "where is my order?", "expected_output": "Ships in 2 days."},
])

Then either run the candidate locally and score it yourself, or hand the dataset to the server-side judge. Local first — scorers are functions that return one or more named scores, and are called scorer(output, expected_output, case) (extra arguments are dropped to match the function's arity):

def correctness(output, expected):
    return {"correctness": 1.0 if expected.lower() in output.lower() else 0.0}

result = client.evaluate(
    "support-golden",
    task=lambda item: answer(item),          # item is the case's input
    scorers=[correctness],
    name="prompt-v4 candidate",
)

print(result.total, result.failures)
print(result.averages)      # {"correctness": 0.91}
print(result.summary())

Every case becomes a real trace tagged with the experiment name, and every scorer verdict lands on that trace — so the run shows up under Evaluations next to production traffic. To have the platform judge the dataset instead, start a server-side run and poll it:

run = client.experiments.run(
    "support-golden",
    judge_model="gpt-5",
    name="prompt-v4 candidate",
)
evaluation_id = run["id"]              # run() returns the evaluation record
detail = client.experiments.get(evaluation_id)

client.datasets gives you list, create, add_items and items; client.experiments gives run, get, list and evaluate (client.evaluate(...) is the shortcut used above). Each run appears under Evaluations with its judged average, so a candidate can be compared against the baseline before it ships.

Redaction

Redaction runs in your process, before anything leaves it. Twelve entity classes are recognised without a server-supplied pattern:

api_key · aws_access_key · credit_card · email · iban · ip · ipv4 · ipv6 · jwt · phone · ssn · url

from fulcrum_ops import RedactionRule

fulcrum_ops.configure(
    agent="Support Bot",
    redaction=[
        RedactionRule(name="contact-details", entity_types=["email", "phone"]),
        RedactionRule(name="cards", entity_types=["credit_card"],
                      applies_to=["input", "output"],
                      replacement="[removed]"),
    ],
)

Rules apply to input and output by default; metadata is also available. The default replacement is [redacted by policy].

Batching, flushing and self-monitoring

Nothing about reporting blocks your agent. Items are enqueued to an in-memory deque and a background worker cuts batches on item count, byte budget or a flush interval.

OptionDefaultNotes
batch_max_items100Items per batch.
batch_max_bytes4 MiBA 413 response halves the batch and retries.
flush_interval_seconds5Time-based cut.
max_queue_size10,000Bounded. On overflow the oldest item is dropped so your agent never blocks.
retry_max_attempts3Exponential backoff with full jitter, honouring Retry-After.
on_error—fn(error, operation). Set this during first integration.
 
client.flush(timeout=10)   # returns False on timeout, never raises
client.close()             # idempotent; an atexit hook also flushes
client.stats()             # submitted / sent / accepted / rejected / blocked / dropped_overflow / dropped_failed

A 200 does not mean every row was accepted

Batches are partial-success. Check client.stats() for a non-zero rejected count — the usual cause is agent_unprovisioned, meaning the agent name does not exist in the workspace or your key is bound to a different one.

Errors

Every failure is a typed subclass of FulcrumOpsError, so you can catch the ones you care about and ignore the rest.

ConfigurationError · ApiError · AuthenticationError · PermissionDeniedError · QuotaExceededError · EntitlementError · ValidationError · NotFoundError · PayloadTooLargeError · RateLimitError · ServerError · TelemetryUnavailableError · TransportError · NetworkError · TimeoutError

Telemetry failures never propagate into your agent path — they surface through on_error and the stats counters instead.

TypeScript SDK

@fulcrum-ops/sdk — ESM and CJS, zero runtime dependencies (it uses global fetch), Node 18+ or a browser. The same env vars and defaults as Python, with two differences: there is no FULCRUM_OPS_DISABLED (pass enabled: false in code to turn it off), and the timeout variable is FULCRUM_OPS_TIMEOUT_MS in milliseconds, not FULCRUM_OPS_TIMEOUT_SECONDS.

import { FulcrumOps } from "@fulcrum-ops/sdk";
import { trackOpenAI } from "@fulcrum-ops/sdk/openai";

const fulcrum = new FulcrumOps({ agent: "Support Bot", environment: "Production" });

await fulcrum.trace("answer", async () => {
  await fulcrum.span({ name: "retrieve", type: "tool" }, (s) => {
    s.setOutput({ docs: 2 });
  });

  await fulcrum.span({ name: "generate", type: "llm" }, async (s) => {
    s.setModel("gpt-5", "azure");
    s.setUsage({ promptTokens: 180, completionTokens: 42 });
    s.setOutput("Ships in 2 days.");
  });
});

await fulcrum.close();

Tracing is callback-style rather than decorator-style; nesting uses AsyncLocalStorage on Node and a stack fallback in browsers. Subpath exports: ./openai, ./anthropic, ./langchain.

Onboarding an existing agent

Connecting an agent is the same five steps every time: register it, mint a key bound to it, instrument the entry point, wire the environment, and verify a run actually arrived. That sequence ships as a skill at skills/connect-agent/, so an assistant can do it against a repo rather than a person doing it by hand.

Point it at an agent codebase and it will read the code to find the entry point, the model calls and any safety checks already present; register and activate the agent; mint a bound ingest key; add the dependency and the instrumentation; place the key where that runtime expects secrets; then run the agent once and confirm the run is visible with the right agent, model, tokens and span tree.

The step it refuses to skip

The skill will not report success on an unverified integration. "It should be reporting now" is not the deliverable — a run visible in Live Runs is, with its model populated and its tokens non-zero. If nothing arrived it works the diagnosis list instead: key present in the process, agent Active, stats() showing rejections, base URL reachable from where the agent runs.

Platform — Live Runs

Live Runs

#/live-runs · every role can read

Real-time observability of agent executions across every connected platform. This is the screen you leave open.

The window. Every figure on the screen answers the window chosen in the Time Range filter: the last hour, the last 6 hours or the last 24 hours (the default). Each card compares it with the window of equal length immediately before.

KPI row: Total Runs, Success Rate, Avg Latency, Policy Violations and the LLMs Used panel. Beneath them, smaller trend tiles for tokens used, estimated cost, fallback rate, human escalations and agent hand-offs. Policy violations, human escalations and agent hand-offs mean exactly what Core concepts defines, for this window.

Success Rate is successful runs (Completed or Warned) over finished runs. A run still in flight counts toward Total Runs but not toward the rate — it has neither succeeded nor failed yet — so a window whose runs are all still running shows a dash rather than 100%. LLM Usage uses the same definition, so the two agree over the same window.

Which filters the cards answer. The run figures follow the Time Range, Tenant and Source filters. Policy Violations and Human Escalations follow the Time Range only: they count every violation record in the workspace for the window, because a violation record names its agent, not the run's tenant or source. When a Tenant or Source filter is set, a note beneath the cards says that it does not narrow those two. The Status, Risk, Policy and search filters narrow the table, not the cards.

LLMs Used is a donut of the runs in the window by model — the same runs the Total Runs card counts, so its slices add up to that card. Each run is counted under the model shown in its Model column: the model the run recorded or, when it recorded none, the model its agent is registered with. The five most-used models get a slice each and any others share an Other slice. A run whose model is known neither way is not dropped: it forms a grey Model not recorded slice. Hover a legend entry for its runs, tokens and cost; click the panel to open LLM Usage for the full breakdown. LLM Usage opens on its own window (24 hours, 7 days or 30 days), so its counts match the panel when both show the last 24 hours.

When the window is capped. A busy window is read newest-first up to a scan limit. When that limit is reached a note beneath the cards says how many runs were read and from when the window was read whole. The run figures — the donut included, which says so itself — are then a floor for the window rather than a complete count, and their trend deltas are withheld. Policy Violations and Human Escalations are counted from the violation records rather than from the runs read, so they stay complete and keep their trend.

Live stream: a server-sent event connection pushes new runs as they arrive, reconnecting with exponential backoff up to 30 seconds if the connection drops. The LIVE badge in the header tells you the stream is attached.

Filters: free-text search, tenant, source platform, status (Completed, Warned, Failed, Running), risk, policy result (Allowed, Warned, Blocked) and a time range.

Table columns: run id, source, agent, status, model, input preview, tools, tokens, cost, duration, confidence, risk, policy, tenant, time.

Click any row for the run inspector: execution summary, prompt and response, model and cost, tools and connectors, guardrails and policy verdicts, retrieval and citations, errors and fallbacks, and audit and replay. From there, View Full Trace opens the span tree and Replay hands off to Replay Studio.

Also here: flag a run for review, and export the filtered set as CSV.

Replay Studio

#/replay · reached from a run, or directly

Step through a recorded execution with its prompt, retrieval, tool and guardrail context. Where Live Runs tells you what happened, Replay Studio shows you in what order — the span tree with timings, so you can see the model call that took six seconds, the tool that returned nothing, or the guardrail that fired between them.

Use it when an answer was wrong and you need to find the step that made it wrong.

The run browser. The rail on the left holds an agent's complete run history — pick an agent, and every run it has ever recorded is listed newest first, each row with its status, time, input preview, tokens and duration. Unlike Live Runs there is no time window: Load older runs pages back through the whole history until the rail says "Full history", so a run from months ago is as reachable as one from this morning. Clicking any row loads its replay.

Arriving from Live Runs — the row action, the inspector's Replay button, or the trace view — loads that run directly and selects its agent in the browser. A run that genuinely cannot be loaded says so and leaves the browser usable, rather than quietly substituting a different execution.

Metrics

#/metrics

Platform-wide execution, latency, token and cost trends over a selectable window (24h, 7d, 30d, 90d), each KPI measured twice — once over the window, once over the window immediately before it — so a delta compares equal spans of time.

Six KPI cards: total runs, success rate, p50 latency, p90 latency, tokens, cost.

Eight series on the API you can overlay on shared axes: runs, success_rate, latency_p50, latency_p90, tokens, cost, violations, escalations; the screen's charts draw runs and cost. The first six come from the telemetry engine; the last two are read from your own governance tables and land on the same bucket grid so one chart can carry both. violations buckets the policy violation records defined under Core concepts. escalations buckets approval requests escalated to a senior reviewer, by when each request was raised — the Approvals screen's Escalated status, not the human escalations Live Runs and the Policy Center count. Both are counted for the whole workspace: the agent filter below does not narrow them.

Breakdowns: per-model usage (runs, tokens, cost, share) and per-platform runs. Export the whole daily table as CSV.

Per-agent metrics. The agent picker beside the window control narrows every number on the screen — KPIs, both charts, the model table and the export — to one agent. The same filter is available on the API as a repeatable agent_id parameter on /metrics/summary, /series, /models, /platforms and /export, so you can compare a few agents in one call. Agent Registry has a View Metrics row action that arrives here with the filter already set.

Why a latency percentile can be blank

Percentiles are combined across agents as a runs-weighted mean, because no cross-project percentile exists. If the store reports no series for a bucket, the chart is empty there rather than interpolated — a neighbouring percentile is a different number and showing it under this name would be a lie.

LLM Usage

#/llm-usage · Platform group · every role can read

Which models your agents use, how much, and which of them give the best results. Reached from the sidebar, or by clicking the LLMs Used panel on Live Runs.

The window. A window selector sets the period every figure on the screen answers: the last 24 hours, 7 days or 30 days. It is the screen's own, not Live Runs', so the LLMs Used panel and this screen count the same runs when both show the last 24 hours.

How a run is attributed. The unit is the run — one agent execution, one row of Live Runs — not the LLM call. Each run is counted once, under the model its Live Runs Model column shows: the model the run recorded or, when it recorded none, the model its agent is registered with. A run that called two models is counted under the one it recorded. Runs whose model is known neither way form a Model not recorded row rather than being left out, so the shares add up to all the runs read. A run attributed from the registration is the agent's configured model, not a record of what ran; the per-agent breakdown sets the two side by side.

What is used, and how much. One row per model: runs and share of the window, input and output tokens, cost and cost per run, the providers recorded on its runs, and the agents using it. Tokens and cost are a dash for a model none of whose runs recorded them. This is where an unexpected model — a deployment alias nobody meant to ship, an expensive model on a cheap task — shows up.

Which give the best results. Leaders are named one measure at a time, never as a blended score, and only among models with enough evidence: at least 20 runs on the measure, or 10 ratings for feedback. Runs with no known model are never ranked.

  • Success rate — successful runs (Completed or Warned) over finished runs (Completed, Warned or Failed). Runs still running are left out; the sample is the finished runs.
  • Feedback rating — the mean 1–5 rating of the Feedback & Quality Loop records that name one of the model's runs. A model nobody rated shows a dash, not a zero.
  • Cost per successful run — the cost of all the model's finished runs, failures included, divided by the runs that succeeded, so a cheap model that fails often is not flattered. A model whose recorded cost is $0 is not ranked: the store records zero when it holds no price for a model, and "free" would win every time.
  • Median latency — the p50 of the model's run durations, computed from the runs themselves, which one slow outlier cannot move.

Each leader is shown with its sample — the finished, successful or timed runs, or the ratings, behind the figure — and models tied on the same value are named with it. When no model has the minimum sample, that measure has no leader and says so rather than naming one. Read the sample before acting on a ranking.

Per-agent breakdown. One row per agent and model: runs, the model's share of that agent's runs, success rate, tokens and cost, beside the model the agent is registered with. An agent running on something other than its registered model stands out, and you can see whether a model's results hold across agents or come from one of them.

Violations and guardrail events per model. A violation record or guardrail event is counted against a model only when its trace id is one of that model's runs. A record for an item that was blocked before it was stored, or for a run outside the rows read, names no run here, so the per-model counts can add up to less than the window's total for the same scope. Both are reported; for violations and human escalations the window's total is the figure Live Runs and the Policy Center count, over this screen's window.

Nothing here is a composite

There is no single "best model" number, because success, feedback, cost and speed trade against each other differently for every workload, and any weighting would be a choice the screen made for you. Each measure stands on its own with the evidence behind it. The figures come from the same capped scan Live Runs reads. When a window holds more runs than one scan reads, the screen says so: the per-model figures then describe the newest runs of the window rather than all of them, and the platform's uncapped count of runs in the window says what share of it they cover.

On the API: GET /api/v1/llm-usage with window (24h, 7d or 30d; 7d when omitted), an optional repeatable agent_id and an optional environment.

Agent governance

Hosting & Deployment

#/connections · member to edit

The platforms your agents are hosted on, the traffic flowing through them, and their health.

Add Connection takes a name, a kind, an endpoint URL and free-form metadata pairs such as Environment or Authentication. The kinds fall in two groups: the agent platforms (Azure AI Foundry, Copilot Studio, M365 Copilot, Power Platform, Custom Agent) — the kinds whose traffic can be attributed to agents — and the infrastructure kinds (MCP Server, Vector Database, Microsoft Purview, Custom REST API), which cannot host an agent and are governed through their tools instead.

Test Connection probes the endpoint and reports what came back. The probe carries no credentials, so it answers reachability only — and a 401 is a healthy answer, because it proves the endpoint is up and guarding itself.

Sync pulls the current state. Test All and Sync All do the whole list. Every test, sync and registration is recorded in the activity feed below the table, and connection health is charted beside it.

Tool Calls & Data answers the question health cannot: is anything actually using this. It lists every tool the agents on this platform called — with call counts, error rate, average duration and when it was last used — and the retrieval and data operations alongside them, over a 7, 30 or 90 day window.

Nothing there is declared on the connection. It is derived from the spans of agents whose platform matches the connection's kind, so an empty result means no agent reported through it in the window — a different statement from the connection being unhealthy, and the screen says which of the two it is.

There is a third case, and it is said plainly rather than shown as a zero. Connection kinds are a superset of agent platforms: an agent runs on Azure AI Foundry, but nothing runs "on" a Vector Database or a Custom REST API. For those kinds traffic cannot be attributed at all, the response sets attributable: false, and the panel says so and points at Connector & MCP Governance, which is where tools reached through them are governed. On the API this is GET /connections/{id}/traffic?window_days=30.

Agent Registry

#/agents · member to create

Every AI agent across your organisation, and the front door for registering new ones.

New Agent requires a name and takes platform, environment, agent type (Pro-code, Low-code, Copilot), risk level, description and an owner. Registration is what creates the agent's telemetry namespace, so nothing can report until this exists.

Lifecycle: agents start Pending Review and move to Active or Inactive. Only listed transitions are allowed; anything else is refused with a 409. An inactive agent cannot ingest.

Row actions: activate, deactivate (with a reason), clone, run, export the configuration manifest, and delete. Edit Agent also sets the model the agent is registered with; a run that records no model of its own is counted under it on Live Runs and LLM Usage.

The Policy Violations card counts the workspace's policy violations over the last 30 days, as defined under Core concepts, against the 30 days before.

Agent Detail

#/agent/<id> · click any agent

Nine tabs covering everything known about one agent:

Overview — status, owner, risk, environment, and its run statistics for the window; its Violations (30d) and Human Escalations (30d) are the policy violations and human escalations defined under Core concepts, for this agent. Runs — its executions, the Live Runs table scoped to this agent. Model & Prompt — the model it is configured with and its system prompt. Tools & Connectors — what it is granted permission to call. Security & Access — access scope and controls. Memory & State — its stores and sessions. Evaluations — quality results for this agent. Configuration — the versioned config, where you commit a new prompt version and diff two versions against each other. Audit Trail — every governance change made to this agent, in order.

Version history is real: each commit of the system prompt is a version, and the diff view shows exactly what changed between any two.

Connector & MCP Governance

#/connectors · member to register operator to block

Govern and monitor all tools, connectors and MCP servers agents may use. Tabs scope the list to All Connectors, MCP Servers, Tools, External Systems and Data Sources.

Add Connector takes a name, a type (API, MCP Server, Database, Vector Store, Custom Tool), provider, risk level, access level (Read, Read-Write, Admin), data classification, auth mode, endpoint URL and scopes.

Three further type values — Connector, Data Source and Tool — are legacy groupings: the dialog no longer offers them, but rows registered through the API may still carry them and the tab filters still honour them. Treat a Tool row as a Custom Tool that predates the current vocabulary.

Block requires a reason and is the interesting state change. A blocked connector keeps its row, its grants and its history, and every agent holding a grant fails closed against it from that moment. That is how you stop a tool estate-wide without editing a single agent.

Why this screen can be empty while agents are running

Connectors are a registry, not a discovery feed. Nothing here is created from observed traffic: a connector exists because a person registered it and granted it. That makes "what this agent may call" an approval decision rather than an inventory of what it happened to call.

Policy Center

#/policies · admin

Create, manage and enforce the rules that run on every ingest. Tabs filter by category: Access Control, Guardrails, Data Protection, Approval & Escalation, Routing & Orchestration, Usage & Quotas, Logging & Retention, Security, Compliance.

Create Policy takes a name, category, enforcement, scope, risk level and status. Optionally supply a rules JSON object; omit it and the server derives one.

FieldValues
EnforcementBlock, Require Approval, Escalate, Mask, Route, Throttle, Warn, Log Only
ScopeGlobal, Environment, Agent, Connector — anything but Global needs a scope_ref
StatusActive, Inactive, Warning, Pending Review

Actions: activate, deactivate (with a reason), clone, import and export a policy bundle as JSON. A Violations view lists what each policy has actually caught, which is the honest test of whether a rule is doing anything.

KPI rows. The first row describes the policies themselves: Total Policies, Active Policies, Warning and Pending Review. The second counts over the last 30 days: Policy Violations (30d), Human Escalations (30d), Blocked Actions (30d) (violations enforced as Block) and Policies Violated (30d). The violations and escalations are exactly those defined under Core concepts — the same records Live Runs counts, including those of agents since removed from the registry — and the table's Violations (30d) column counts the same records per policy, so its rows add up to the cards.

Why Live Runs shows fewer. Live Runs shows at most 24 hours, so its Policy Violations and Human Escalations are lower whenever anything fired earlier in the month; the two agree when the windows do. On the API, GET /api/v1/policies/summary?window_days=1 counts the last 24 hours, the window Live Runs opens on.

Policies reach an agent either by explicit binding or by scope match, and per-agent or per-tag exceptions remove specific agents from a rule that would otherwise cover them.

Approvals & Audit

#/approvals · approver

The human-in-the-loop queue, plus the tamper-evident record of everything that has happened.

Approvals: requests raised by a Require Approval or Escalate policy — typical triggers are a financial action above a threshold, a bulk data export, an external communication, or a production config change. Approve, reject, escalate, or add a comment; every decision records who, when and why.

Audit: an append-only, hash-chained trail of every governance action across every screen, filterable by actor, action, entity and time. Verify re-walks the chain and confirms no row has been altered or removed — the point of hash-chaining is that tampering is detectable, not merely discouraged.

Export either view as CSV for a compliance reviewer.

Configuration

Configuration Center

#/configurations · admin to edit

Manage and version every configuration asset. Tabs: All Configurations, Models, Prompts, Tools, Guardrails, Routing, Quotas, Environments, Connectors.

Each configuration is versioned, so you can see what changed, when, and by whom — and roll back. Prompt Studio

#/prompts · member to author

Author, version, review and approve system prompts across all agents. Prompts live in the telemetry engine prompt library under the agent namespace, so a commit list is a real version history.

Create a prompt with a name and template, commit new versions, diff versions, and pull them at runtime with get_prompt(). Because the version used is recorded on each run, a quality change can be traced to the exact wording that caused it.

Running a prompt

Run Prompt renders the template with one variable set and sends it to a model, returning the answer, the provider's own token counts and the round-trip latency — so a wording change can be judged on output, cost and speed together. Optionally override the model, add a system message, or cap output tokens.

This is the one place the server calls a model itself, so it is off unless configured. Set FULCRUM_OPS_PROMPT_STUDIO_ENDPOINT and FULCRUM_OPS_PROMPT_STUDIO_API_KEY (plus optionally _MODEL, _API_VERSION, _MAX_OUTPUT_TOKENS) and restart. Any OpenAI-compatible chat completions endpoint works — OpenAI, Azure OpenAI, or a local gateway; Azure is detected from the endpoint and authenticated with its own header. Unconfigured, the editor still renders and diffs, and only Run is refused — naming the missing setting rather than failing obscurely.

Every run is audited as prompt.executed. It is deliberately not recorded as an agent run: no agent executed it, and folding a person's experiment into the figures the platform reports as agent behaviour would corrupt them. On the API: POST /prompts/{id}/execute. Use /test instead to render and score a whole dataset without calling a model.

RAG & Knowledge Governance

#/knowledge · member to add

Five tabs governing what your agents retrieve from: Knowledge Sources, Vector Indexes, Retrieval Policies, Citations & Grounding and Data Access & Lineage.

Register a source, watch its sync status (Active, Syncing, Failed), set retrieval policies, and review grounding quality — retrieved document counts, grounding scores, citation accuracy and source freshness, all of which also appear per-run in the Live Runs inspector.

Data Access & Lineage answers the question an auditor asks: which agents can reach this source, and where did this answer material come from.

Secrets & Credentials

#/secrets · admin admin + justification to reveal

The vault for credentials your agents use to reach other systems. Tabs: All Secrets, API Keys, OAuth Clients, Certificates, Service Principals, Connector Credentials.

This is the most locked-down screen in the product, and deliberately so.

  • Material enters on create and rotate only, and is encrypted before it touches a row. The plaintext is never written to a log line, an audit detail or a CSV cell.
  • Reading a value goes through one path that demands the admin role and a written justification, and refuses disabled or revoked credentials outright.
  • Every reveal writes two independent records: an access-log row for operators and an audit-chain row for compliance.
  • A refused attempt is evidence too. Denials are committed before the error unwinds the request, because who tried and was stopped is exactly what the failed-attempts counter exists to show.

Lifecycle governance: rotation periods with overdue tracking, expiry warnings, per-secret ownership and risk classification. A secret may also hold only a reference to material living in an external vault — Key Vault, Secrets Manager — in which case has_material is false and this platform governs who may use it, when it rotates and who touched it, without ever holding the value.

Not the same thing as API Access Tokens

Secrets are credentials for traffic going out, and are encrypted because the value must be retrievable. API keys are credentials for traffic coming in, and are hashed because they never need to be read back. Different direction, different storage, different screen.

Quota, Cost & Capacity

#/quota · operator to edit budgets

Views: a cost breakdown by service and by team, usage and capacity time series, a forecast, top drivers of spend, and an events feed of quota trips.

Memory & State Management

#/memory · operator

Govern agent memory, session state and conversation context across environments.

Memory stores — what persists between runs. Sessions and Conversations — live and historical context, grouped by thread. Agent state — what each agent is currently holding. Retention policies — how long any of it survives. Backups — snapshots you can restore from.

Actions include purge, backup and restore. Retention is where the compliance answer lives: an agent that remembers a customer indefinitely is a data-protection problem, and this screen is where you bound it.

Environments & Releases

#/deployments · operator

Environments, releases and rollouts for every governed agent. The default environments are Production, Staging, UAT, Development, QA, Sandbox and DR.

A deployment moves an agent version through stages. Actions: promote to the next stage, halt a rollout in progress, approve a gated stage, roll back to the previous version, and restart an environment.

Quality

Evaluations

#/evaluations · member to run

LLM quality evaluations across agents — correctness, grounding, faithfulness and safety.

Run an evaluation against a dataset, either from this screen or from the SDK with client.experiments.run(...). Each completed run records a judged average, and the trend chart plots those averages over time so a regression is visible rather than anecdotal.

Compare puts a baseline and a candidate side by side — the question you actually have before shipping a prompt change. Datasets are shared with the SDK, so a case added in code appears here.

Guardrails

#/guardrails · admin to configure

Runtime safety filters for prompts and responses: prompt injection, PII, toxicity, hallucination and secrets.

Configure a guardrail, set its action — Warn, Block, Mask or Log — and watch the events feed for what it has caught, with the matched entity counts and a sample of the offending text. The inline content checker on this deployment implements the PII, Topic and Prompt Injection validations; a guardrail whose type it does not implement cannot be tested (the Test button answers plainly rather than inventing a verdict).

Guardrails run at ingest, so a Block verdict refuses the item before it is ever stored, and Mask strips the content while keeping the record that something happened. Agents can also report their own guardrail verdicts via log_guardrail_event(), which is how a check that runs inside your process still shows up here.

Testing & Regression Suite

#/testing · member

Seven tabs: Test Suites, Test Runs, Datasets, Evaluations, Baselines, Schedules, Environments.

Build a suite, run it against an environment, and compare the result against a recorded baseline — the mechanism that turns "it seems worse" into a number. Schedules run suites automatically, which is what makes regression testing continuous rather than remembered.

Feedback & Quality Loop

#/feedback · member

Alerts

#/alerts · member to act admin for rules

Licensing & Entitlements

#/licensing · owner

SymptomCause and fix
Agent runs, nothing appears in Live RunsCheck client.stats(). A non-zero rejected count with agent_unprovisioned means the agent name does not exist in the workspace, or your key is bound to a different agent. Register and activate the agent, or rebind the key.
Everything is silently not reportedNo FULCRUM_OPS_API_KEY. The SDK disables itself by design and your functions still run. Check /health on your agent or print client.enabled.

A telemetry screen shows telemetry_unavailableThe engine is unreachable. Governance screens keep working. Check the engine container and /health, which reports "telemetry": false when the adapter cannot reach it.

When you are unsure whether it is you or the platform

Set on_error on the client and turn on FULCRUM_OPS_DEBUG. Every transport failure, rejected row and retry prints with the server own message. Most first-time integration problems announce themselves in the first thirty seconds of doing this.
